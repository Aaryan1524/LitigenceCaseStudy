# Litigence Parallel Filings

My submission for the Litigence live exercise (`parallel-filings-brief.md`).
The system is a multi-tenant docket service: signed webhooks, an extraction
worker and a review API on SQLite. The exercise is judged on how the agents
are set up, directed and checked, so this README is mostly about that.

I didn't finish in the live hour. I rebuilt it afterwards, at the
interviewer's invitation. The timeline is at the bottom.

## What I did

**Planned before any code.** I wrote one contract (`docs/contract.md`):
schema, statuses, function signatures and every HTTP response. Every agent
built against it, never against another agent's code. When requirements
changed mid-build, I changed the contract and pushed the change to the
agents it affected.

**Split the work into five agents and a reviewer.**
- api: intake, review API, database.
- worker: the extraction loop and its checks.
- extract: the text parser.
- tests: written from the contract only.
- evals-data: the 20 labelled notices.
- reviewer: read the finished code.

extract, api and tests ran in parallel. The worker started automatically
when api's database was ready.

**Defined each role in a file** (`.claude/agents/<role>.md`): its model,
tools and a short prompt. The small parsing job ran on Haiku for $0.01. The
rest ran on Opus.

**Gave each agent only what it needed.** Each one got a single context file
with its task, its plan and only the contract sections it uses (600 to
1,000 words, generated by `scripts/packs.py`). Each agent worked in its own
git clone, with only its own files on disk.

**Kept the two required separations physical.**
- The agent writing the eval data was a single LLM call with no tools, so
  it could not open anything.
- The tests agent had no way to run code.
- A script enforced the order: extract had to finish before the eval data
  existed anywhere on disk.

**Didn't take "done" on trust.** A hook stopped any agent from finishing
with uncommitted work, files outside its slice, or code that doesn't
import. Tests came from a different agent than the code, and a fresh
reviewer read the integrated result.

**Made every action traceable.**
- A git hook the agents couldn't reach stamped every commit with the
  agent's role and session id.
- Every tool call went to a log where each line is chained to the
  previous one by hash, so edits show up.
- An audit script (`scripts/audit.py`) checks that the files an agent was
  forbidden to see never entered its git history. Each check also has a
  negative test showing it can fail.

**Had the tests written a second time, separately.** After the build, I
moved the original tests off `main`. I had Codex write a new suite and eval
set from an export of the code and the contract, with no access to the
originals. I then ran each suite against the other's deliberate defects.

## What went wrong

I kept these in the record ([evidence/incidents.md](evidence/incidents.md)).

1. A context file was missing the seed data. The agent stopped and asked
   instead of inventing it. I fixed the contract.
2. My stop hook blamed the worker for files I had merged in. The agent
   refused to work around it. I fixed the hook.
3. My script failed to save the eval data. I recovered it without a second
   model call.
4. I accidentally let code reach the tests agent's git history. It was
   never on disk and the agent couldn't run code, but the audit still
   flags it. The script now refuses to let it happen again.

## What I think breaks first in production

1. SQLite write contention. Blocking database calls inside async handlers
   stall every request.
2. Notices stuck in `processing`. Nothing recovers a crashed worker.
3. Malformed but signed requests return 500, and the vendor retries
   forever.
4. One plaintext secret per tenant, no replay protection and no key
   rotation.
5. Regex extraction on real court notices. It needs a model behind the
   same validation step.
